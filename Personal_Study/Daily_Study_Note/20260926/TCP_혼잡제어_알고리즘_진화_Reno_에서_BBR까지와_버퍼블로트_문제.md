# TCP 혼잡제어 알고리즘 진화(Reno→BBR)와 버퍼블로트 문제

> 2026-09-26 신규 주제 · 확장 대상: 통신 네트워크

## 학습 목표

- TCP Reno의 AIMD(Additive Increase Multiplicative Decrease) 기반 혼잡 회피가 손실을 신호로 해석하는 원리와 한계를 설명한다
- CUBIC이 고대역폭·고지연(BDP) 네트워크에서 Reno보다 빠르게 수렴하도록 설계된 지점을 구분한다
- 버퍼블로트가 발생하는 구조적 원인과 손실 기반 혼잡제어가 이를 악화시키는 메커니즘을 재현한다
- BBR이 손실이 아닌 대역폭·RTT 측정 모델로 혼잡을 추정하는 방식을 기존 알고리즘과 대비한다

## 1. 혼잡제어가 필요한 근본 이유

TCP는 종단 간 프로토콜로, 송신 측은 네트워크 중간 경로(라우터, 스위치)의 실제 혼잡 상태를 직접 알 수 없다. 만약 모든 송신자가 자신의 처리량을 무한정 늘리면 중간 라우터의 큐가 넘쳐 패킷 손실이 발생하고, 손실된 패킷의 재전송이 다시 트래픽을 늘려 혼잡을 더 악화시키는 혼잡 붕괴(congestion collapse)로 이어질 수 있다. 1980년대 실제로 이런 붕괴가 관측된 이후 Van Jacobson이 제안한 혼잡제어 알고리즘이 오늘날 모든 TCP 구현의 기반이 되었다. 핵심 아이디어는 "네트워크로부터 받는 간접적인 신호(손실, 지연)를 관찰해 송신 속도를 스스로 조절한다"는 것이다.

## 2. AIMD와 Reno의 동작

Reno는 혼잡 윈도우(cwnd, congestion window)라는 변수로 한 번에 보낼 수 있는 미확인 데이터량을 제한한다. 손실이 없으면 매 RTT마다 cwnd를 조금씩(선형적으로) 늘리고, 손실이 감지되면 즉시 절반으로 줄이는 AIMD 규칙을 따른다.

```
손실 없음: cwnd = cwnd + 1 (RTT당 1 MSS씩 증가, 선형)
손실 감지(3중복 ACK): cwnd = cwnd / 2 (즉시 절반으로 감소)
손실 감지(타임아웃): cwnd = 1 (슬로우 스타트로 재시작)
```

이 선형 증가·급격한 감소 패턴은 "톱니파(sawtooth)" 형태의 처리량 그래프를 만든다. AIMD가 공정성과 안정성을 동시에 보장한다는 수학적 증명(체이유·자인의 공정성 분석)이 있어 수십년간 표준으로 자리잡았지만, 문제는 대역폭이 크고 지연(RTT)이 긴 네트워크, 이른바 고 BDP(Bandwidth-Delay Product) 네트워크에서 이 선형 증가가 지나치게 느리다는 점이다. 예를 들어 RTT 100ms에 10Gbps 링크에서 완전히 대역폭을 채우려면 이론상 수만 RTT, 즉 몇십 분에서 몇 시간이 걸릴 수 있어, 손실이 한 번이라도 발생하면 다시 절반으로 줄어들는 패턴이 반복되며 실제 가용 대역폭을 활용하지 못하는 구간이 길게 이어진다.

## 3. CUBIC: 큐빙 함수 기반 증가

CUBIC은 Reno의 선형 증가 대신 3차 함수(cubic function) 형태로 cwnd를 증가시켜, 손실 직후에는 조심스럽게 증가하다가 이전 손실 시점의 cwnd(포화점으로 추정되는 지점)에 가까워질수록 증가 속도를 줄이고, 그 지점을 넘어서면 다시 빠르게 증가하는 곁선을 그린다.

```
W(t) = C(t - K)^3 + W_max
```

여기서 `W_max`는 마지막 손실 직전의 cwnd, `K`는 `W(t)`가 `W_max`에 도달하는 시간, `C`는 증가 속도를 결정하는 상수다. CUBIC의 증가율이 RTT 값에 직접 의존하지 않는다는 점도 중요한 설계 결정이다. Reno는 RTT가 짧을수록 ACK가 자주 와서 cwnd가 더 빠르게 늘어나는 RTT 불공정성이 있는데, CUBIC은 실제 경과 시간 `t`를 기준으로 증가하므로 이 불공정성을 상당부분 완화한다. Linux 커널은 2006년부터 CUBIC을 기본 혼잡제어 알고리즘으로 채택했다.

## 4. 버퍼블로트: 큐가 클수록 나빠지는 역설

버퍼블로트는 네트워크 장비(특히 가정용 공유기, ISP 장비)의 버퍼가 지나치게 크게 설정되어 있을 때 발생하는 현상이다. 손실 기반 혼잡제어(Reno, CUBIC)는 "패킷이 버려져야만" 혼잡 신호로 인식하는데, 버퍼가 매우 크면 패킷이 버려지기 전에 먼저 큐에 오래 쌓이면서 지연 시간이 크게 늘어난다. 이는 화상 회의나 온라인 게임처럼 지연에 민감한 트래픽이, 같은 회선에서 동시에 실행되는 대용량 다운로드 때문에 손실은 없는데도 지연이 급격히 나빠지는 현상으로 체감된다. 버퍼블로트를 완화하기 위한 라우터 측 대응이 AQM(Active Queue Management)이며, 대표적으로 CoDel(Controlled Delay)은 큐에 머무는 시간 자체를 측정해 일정 임계값을 넘으면 버퍼가 가득 찰 전에 미리 패킷을 드롭해 혼잡제어 알고리즘에 조기 신호를 준다.

```bash
# Linux에서 CoDel 기반 큐 규율(qdisc) 적용 예
tc qdisc add dev eth0 root fq_codel
```

`fq_codel`은 CoDel의 지연 기반 드롭과 Fair Queuing(흐름별 공정 분배)을 결합해, 하나의 대용량 전송 흐름이 큐를 독점해 다른 흐름의 지연을 악화시키는 문제까지 함께 완화한다.

## 5. BBR: 손실이 아닌 모델 기반 혼잡 추정

Google이 2016년 발표한 BBR(Bottleneck Bandwidth and Round-trip propagation time)은 손실을 혼잡 신호로 쓰지 않는다는 점에서 이전 알고리즘들과 근본적으로 다른 접근을 취한다. BBR은 대신 두 가지를 직접 측정해 모델을 구성한다: BtlBw(Bottleneck Bandwidth, 경로상 가장 좋은 구간의 처리량 한계)와 RTprop(Round-trip propagation time, 큐잉 지연을 제외한 순수 왕복 전파 지연)이다.

BBR은 이 두 값의 곱(BDP)을 실제 목표 전송량으로 삼아 cwnd와 페이싱 속도(pacing rate)를 조절한다. 손실 기반 알고리즘이 "손실이 날 때까지 밀어붙인 뒤 후퇴"하는 방식이라면, BBR은 "병목의 실제 용량을 추정해 그 용량만큼만 채우고 큐를 쌓지 않는다"는 방식이다.

BBR은 주기적으로 `PROBE_BW`, `PROBE_RTT` 같은 상태를 오가며 모델을 갱신한다. `PROBE_RTT` 상태에서는 의도적으로 전송량을 최소 수준으로 줄여 큐가 비워진 상태에서의 진짜 최소 RTT를 재측정한다.

## 6. 손실 기반과 모델 기반의 공존 문제

같은 병목 링크에서 CUBIC 흐름과 BBR 흐름이 경쟁하면 공정성 문제가 생길 수 있다. CUBIC은 손실이 발생해야 속도를 줄이는데, BBR은 손실이 나기 전에 스스로 속도를 제한하는 경향이 있어, 두 알고리즘이 같은 병목을 공유하면 CUBIC 흐름이 상대적으로 더 공격적으로 대역폭을 점유하고 BBR 흐름이 밀리는 현상이 초기 BBR 버전에서 보고된 바 있다. 이 문제를 완화하기 위해 BBRv2는 손실 신호를 완전히 무시하지 않고 보조적으로 반영하도록 설계가 수정되었으며, ECN(Explicit Congestion Notification) 지원 여부에 따라서도 동작이 달라진다.

## 7. 실전 관측과 알고리즘 선택

```bash
sysctl net.ipv4.tcp_available_congestion_control
sysctl net.ipv4.tcp_congestion_control
# 변경 예
sysctl -w net.ipv4.tcp_congestion_control=bbr
```

BBR을 커널 레벨에서 활성화하려면 페이싱을 지원하는 큐 규율(`fq`)이 함께 필요하다는 점도 실무에서 자주 누락되는 설정이다. `fq_codel`과 달리 BBR이 요구하는 `fq`는 정밀한 페이싱(패킷을 일정 간격으로 흥끩리는 것) 기능이 핵심이라, `pfifo_fast` 같은 기본 큐 규율과 조합하면 BBR의 설계된 이점을 온전히 얻지 못할 수 있다.

## 8. QUIC과 사용자 공간 혼잡제어

전통적인 TCP 혼잡제어는 커널 안에 구현되어 있어 알고리즘 교체가 커널 업그레이드나 sysctl 설정 변경을 필요로 했다. QUIC(HTTP/3의 전송 계층)은 UDP 위에서 사용자 공간(user space)에서 전송 프로토콜 전체를 재구현하면서, 혼잡제어 알고리즘도 애플리케이션과 함께 배포되는 라이브러리 코드로 옥겨졌다. 이는 새 혼잡제어 알고리즘을 실험하거나 배포할 때 커널 패치 없이 애플리케이션 배포 주기로 반영할 수 있게 되었다는 뜻이며, 실제로 Google의 QUIC 구현체는 초기부터 BBR을 기본 혼잡제어로 채택해 커널 TCP 스택보다 먼저 대규모 트래픽에 BBR을 적용한 사례로 꾼힌다.

## 9. 애플리케이션 레벨에서 체감하는 영향

혼잡제어 알고리즘은 커널 네트워크 스택 안에서 동작하지만, 그 선택은 애플리케이션 계층에서 체감되는 지연·처리량 프로파일에 직접 영향을 준다. 모바일 네트워크에서는 실제 혼잡이 아니라 무선 구간의 일시적 신호 저하로도 패킷 손실이 발생하는데, 손실 기반 알고리즘은 이를 혼잡으로 오인해 불필요하게 속도를 줄이는 반면, BBR은 손실 자체보다 측정된 대역폭·RTT 모델을 우선하므로 이런 환경에서 처리량 저하가 덜한 경향이 보고된다.

또한 REST API 서버가 커넥션을 오래 유지하는 롯폴링이나 SSE(Server-Sent Events) 같은 패턴을 쓴다면, 버퍼블로트로 인한 지연 증가가 타임아웃 설정과 상호작용해 예상치 못한 연결 끓김을 유발할 수 있다. 이런 증상을 진단할 때는 애플리케이션 로그만 보지 말고, `ss -ti` 명령으로 소켓별 현재 사용 중인 혼잡제어 알고리즘과 재전송 횟수, 왕복 지연 추정치를 함께 확인하는 것이 원인을 네트워크 계층과 애플리케이션 계층 중 어디서 찾아야 할지 가르는 실전 절차다.

```bash
ss -ti dst 203.0.113.10
# 출력에서 cubic/bbr 표시, rtt, retrans 카운트 등을 확인
```

`retrans` 카운트가 지속적으로 증가하면서도 `rtt` 값이 안정적이라면 무선 구간의 간헐적 손실 가능성이 높고, 반대로 `rtt`가 시간이 지날수록 꿈준히 커지는 패턴이라면 버퍼블로트로 인한 큐잉 지연 누적을 의심할 수 있다.
